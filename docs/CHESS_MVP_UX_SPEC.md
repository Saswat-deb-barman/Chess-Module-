# chess-mvp — user journeys & component spec

Version 0.1. Written 13 July 2026. Feeds Claude Code.
Scope: journeys and component decomposition. UI/visual direction is a separate pass.

---

## 0. The one thing that makes this app different

Chess.com already exists. It is better than anything we will build at playing chess.
It does not know that Saswat stalemates from won positions, that DJ hangs his queen on move 22,
or that the two of them have a rivalry with a score.

**This app is not a chess server with analysis bolted on. It is a rivalry engine with a chess board attached.**

Everything below is ranked against that sentence. The board is table stakes. The council, the
pattern tracker and the scouting card are the product. If a screen does not serve the rivalry
or the improvement loop, it gets cut.

The user group is six friends, not six thousand strangers. That single fact kills a lot of
standard product furniture: no matchmaking queue, no global leaderboard, no onboarding funnel,
no marketing hero. Build for a private table.

## 1. The journeys

### 1.1 The core loop (this is the whole app)

```
Dashboard  ──►  Game  ──►  Result  ──►  Analysis  ──►  Pattern tracker  ──►  Dashboard
    ▲                                                                             │
    └─────────────────────────  "play him again"  ◄───────────────────────────────┘
```

The loop only closes if Analysis writes something back to the Dashboard. If a player finishes
a game, reads the analysis and nothing on the dashboard changed, the app is a toy. The
`PatternHit` component (see 6.7) is the load-bearing piece of the entire product.

### 1.2 First-run journey (a friend gets the link)

```
Link in WhatsApp
  → Landing (sees a live board, sees the league table, sees DJ is 3-2 up on someone)
  → Sign in with Google
  → Allowlist check
      ├─ on list  → Onboarding sheet (display name + piece set, two fields, 15 seconds)
      └─ not on list → "Invite only" wall + request access
  → Dashboard (empty state: "No games yet. Beat the bot once to unlock the table.")
  → Play bot
  → First analysis
  → Dashboard, now with one row and one tracked pattern
```

Target: link to first move in under 45 seconds. Anything that adds a step here gets cut.

### 1.3 Returning journey (the daily use)

```
Dashboard
  → sees "DJ has a room open" OR "DJ beat you 2 hours ago"
  → Join room / Create room / Play bot
  → Game
  → Game over modal: [Rematch] [Analyse]
  → Analysis
  → Dashboard
```

Note the game-over modal. **Analyse is the primary button, not Rematch.** That single
choice is the difference between this app and every other chess app.

### 1.4 The scouting journey (the secret weapon)

```
Dashboard → League table → tap DJ → Scouting card
  (auto-generated from every game he has played on this platform:
   his openings, his tells, his exploit plan, his swindle behaviour)
  → "Play him" button right there on the card
```

This is DJ_SCOUTING_PAGE.md, generated by the LLM instead of by hand, for every player,
refreshed after every game. Nobody else has this. It should be one tap from the dashboard.

## 3. Landing page

**Job:** turn a friend holding a link into a signed-in player. It is a door, not a brochure.
No feature grid. No pricing. No testimonials. One screen, no scroll needed to act.

| Component | Purpose | Notes |
|---|---|---|
| `SiteHeader` | Wordmark + single sign-in action | Nothing else lives here |
| `Hero` | Name, one line of copy, one button | The line should sound like a private club, not a product |
| `LiveBoardBackdrop` | An idle board slowly replaying the group's most recent finished game | Decorative. **Must fail soft.** If the fetch dies, render a static famous position. Uses `Board` in `readOnly` mode |
| `PrimaryCTA` | Google sign-in | Secondary: "Play the bot first" (fork, see 9) |
| `LeagueTicker` | One thin strip: "DJ beat Saswat, 42 moves, 2h ago" | Only renders if games exist. This is the hook for a six-person group |
| `Footer` | One line | |

Six components. One is conditional. That is the correct size for this page.

## 4. Login

Because auth is Google-only, a full login *page* has nothing to put on it. Do not build a
screen whose entire content is one button.

**Decision:** the sign-in button lives on the Landing page. `/auth/callback` exists only to
handle the return trip, the allowlist decision and the failure states.

| Component | Purpose | Notes |
|---|---|---|
| `GoogleSignInButton` | The one action | Handles popup-blocked state |
| `AuthErrorNotice` | Honest failure states | Popup blocked. Server down. Token expired. Say which one |
| `AllowlistGate` | The real feature | Private club. Email not on the list gets "This table is invite only" plus a request-access action. Do not silently 403 |
| `OnboardingSheet` | First login only | Two fields: display name, piece set. Then straight to the dashboard. Never show again |
| `SessionBoundary` | Wraps every `/app` route | Redirects to `/` on expiry, preserves the intended destination |

## 5. Dashboard

**Job:** answer three questions above the fold.
1. Who is around and what is the score.
2. What do I play right now.
3. What did I do wrong last time.

Anything that does not answer one of those three is below the fold or cut.

| Component | Purpose | Notes |
|---|---|---|
| `AppShell` | Topbar, avatar, sign out. Wraps every authed page | Build this first. Everything hangs on it |
| `PlayCard` | The primary action block. Highest-value real estate on the app | Three modes in one card: Play bot / Create room / Join room |
| ├ `DifficultySelector` | Easy / Medium / Hard | **Exists in Phase 1. Reuse, do not rewrite** |
| ├ `TimeControlSelector` | 10+0 default | 5+0 and 15+10 also present. These are the controls the group actually plays |
| ├ `RoomCodeCreator` | Generates a code, shows it big, copy button | Copy button must copy a shareable link, not just the code |
| └ `RoomCodeJoiner` | Four-to-six character input | Autofocus. Uppercase on entry |
| `OpenRoomsStrip` | "DJ has a room waiting" with a one-tap join | For six people this beats a matchmaking queue entirely |
| `LeagueTable` | The head-to-head board. The emotional core | Rows: player, W-L-D, current streak. Tapping a row opens their scouting card |
| `RecentGamesList` | Last five games | Each row: opponent, result, time control, one-line LLM verdict ("Lost on time from a winning position"), link to the analysis |
| `PatternTracker` | My own recurring mistakes with counts and trend | Hanging pieces. Castling timing. Time management. Stalemate traps. **This is the improvement flywheel. It is written to by the analysis screen** |
| `DrillShelf` | Drills generated from my own blunders | Slot it on the dashboard now, populate it in a later phase |
| `WardrobeCard` | Entry point to "dress your queen" | Link only. The wardrobe itself is a later phase |

### Empty states matter here
A new player sees an empty league table and an empty tracker. Write those two empty states as
copy, not as "No data". They are the first thing a friend reads after signing in.

## 6. Game UI

**The tension:** the board must dominate, but four side systems want space (clock, move list,
commentary, council). Two side panels will kill this screen.

**The rule: one board, one right rail, and the rail is tabbed. Never two panels.**

```
┌────────────────────────────────────────────────────────┐
│  [ opponent card: avatar · name · clock · captures ]   │
│                                                        │
│   ┌──────────────────────┐   ┌──────────────────────┐  │
│   │                      │   │  Moves │ Talk │ Council│ │
│   │        BOARD         │   ├──────────────────────┤  │
│   │                      │   │                      │  │
│   │                      │   │      (rail body)     │  │
│   └──────────────────────┘   └──────────────────────┘  │
│                                                        │
│  [ my card: avatar · name · clock · captures ]         │
│                            [ resign  draw  flip ]      │
└────────────────────────────────────────────────────────┘
```

### Design note: the council must be a game mechanic, not an engine leak

An unlimited in-game advisor is just Stockfish with a personality. It ruins competitive games
and it makes every win meaningless.

**Proposal: three consults per game.** Each consult picks one coach and returns a *hint*, never
a move. Tactics Tara: "there is something on the kingside." Endgame Ed: "your rook belongs
behind that pawn." Spending a consult is announced to the opponent: *"Saswat called the council."*
That converts a cheat into a resource with a cost, which is a real game mechanic and is also
funnier.

Council is disabled by default in rated head-to-head games, enabled by default against the bot.

## 7. Post-game analysis

**Job:** not an eval bar. Stockfish gives numbers. The council gives sentences that name your
pattern. That is the whole reason this screen exists.

| Component | Purpose | Notes |
|---|---|---|
| `AnalysisHeader` | Result, opponent, time control, the one-line verdict | The verdict is the sentence that gets screenshotted |
| `ReplayBoard` | `Board` in `replay` mode | Keyboard arrows must work. Non-negotiable |
| `EvalGraph` | The ribbon across the game | **This is the navigation spine, not a statistic.** Click a spike, jump to the move. Blunders marked |
| `MoveTable` | Every move classified | Best / good / inaccuracy / mistake / blunder, from depth-limited Stockfish |
| `CriticalMoments` | Three to five cards | Each: position thumbnail, what you played, what was there, one paragraph. Generated from the engine's biggest eval swings. Cheap to produce, highest value on the page |
| `CouncilVerdicts` | The five coaches, one card each | The Historian on the opening. Tactics Tara on the missed shots. Strategist Sam on the plan. Endgame Ed on the conversion. Coach Priya last, tying it to the tracker. **A coach with nothing to say does not speak.** Silence is a feature |
| `PatternHit` | "This game added +1 to Hanging pieces. Now 8." | **This writes back to the dashboard tracker. This is the component that closes the loop. If you build nothing else on this screen, build this** |
| `DrillGenerator` | "Turn move 42 into a drill" | Produces an interactive position like checks_only_drill.html, in-app. Later phase, slot it now |
| `ShareCard` | Export a PNG of the critical moment | Straight into the group chat. Low cost, high social return |
| `PgnExport` | | Exists |

### Engineering note: analysis runs once, server-side, and is cached

Analysis is the most expensive thing in the app: an engine pass plus five LLM calls.

- Run the engine pass **server-side on game completion**, not on page load.
- Store the analysis JSON on the game row in Neon.
- Generate the council text **once** and store it. Never regenerate on refresh.
- The analysis page reads a cached row. It should load instantly and cost nothing.

If this is done on the client at page-open, every refresh costs money and the page takes
twenty seconds. Decide this before writing the screen, not after.

## 8. Shared component layer (build these first)

These are used across three or more screens. Getting them right once saves rewriting them four times.

- `Board` (four modes: bot, live, replay, readOnly) — used on Landing, Game, Analysis, Drills
- `PieceSetRenderer` — the wardrobe seam
- `PlayerCard`, `Avatar`, `Clock`
- `CouncilAvatar` — the five coaches, used in Game, Analysis and Drills
- `Tabs`, `Modal`, `Toast`, `Card`, `Button`
- `AppShell`

## 9. Open forks (answer these before UI work starts)

1. **Guest play on the landing page.** Can a stranger play the bot without signing in? Yes means
   no auth guard on `/play/bot` and no DB write. No means the landing page has exactly one action.
   This changes routing and the Landing component list.
2. **The council in-game.** Adopt the three-consult mechanic above, disable it entirely for
   head-to-head, or something else?
3. **Live only, or resumable?** If DJ closes his laptop mid-game, does the room die or does the
   game persist and wait for him? Resumable means the dashboard needs an `ActiveGamesStrip` and
   the socket layer needs state in Postgres, not just in memory.
4. **Rating.** Real Elo per player, or just head-to-head W-L-D? For six people, head-to-head is
   more meaningful, cheaper, and harder to game. Recommendation: skip Elo.

---

## 10. Build order

1. `AppShell` + routing + auth guard + allowlist. The skeleton everything hangs on.
2. Dashboard `PlayCard`. Gets a player back into a game in one tap.
3. Game UI with the rail showing `MoveList` only. This is feature-parity with Phase 1, restructured.
4. Post-game analysis, engine only, no LLM. Prove the eval graph and the cached-row pattern.
5. `CouncilVerdicts` + `PatternHit`. The loop closes here. **The app becomes itself at this step.**
6. Room codes, `ChatPanel`, `OpenRoomsStrip`.
7. `CommentaryFeed` + voice. Decorative. Last.
8. Wardrobe.

## 11. Known gaps and the thing most likely to break

Ranked by impact, per the standing handoff rule.

1. **Two realtime channels on one page.** A live socket game plus a streaming LLM commentary
   feed are both open on the Game UI at the same time. This is the single most likely thing to
   break. **Smoke test one streamed commentary line inside a live socket game before building
   the tabbed rail.** Do not discover this at the end.
2. **Analysis cost.** If the engine pass or the council calls run client-side or on every page
   load, cost and latency both explode. Cache on the game row. Decided above, but it is the
   easiest thing to get wrong under time pressure.
3. **Promotion picker.** Still auto-queening. Known, still open, will be noticed the first time
   someone wants a knight.
4. **Captured pieces tray.** Requires FEN diffing. Carried over from the Electron build, still open.
5. **Castling and capture animations.** Carried over. Still open.
6. **Piece set seam.** If `PieceSetRenderer` is not built as a real abstraction now, the wardrobe
   becomes a rewrite of `Board` later.

## 12. What this document does not cover

Visual direction: type, colour, motion, the aesthetic point of view. That is the next pass, and
it should start from the Game UI, not the Landing page. The Game UI is the screen everyone will
actually look at for forty minutes at a stretch. Design it first and let the rest inherit.
